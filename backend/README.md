# Авто-накопления: backend (Me-to-Me round-up → доходный депозит)

Модуль проводит оплату картой и в той же транзакции переводит «сдачу» на накопительный
депозит, где каждый день начисляются проценты (12–20% годовых).

Стек: Python 3.9+ и SQLite, только стандартная библиотека, ничего устанавливать не нужно.

```bash
cd backend
PYTHONPATH=.:tests python3 -m unittest discover -s tests -v   # 57 тестов
python3 -m autosave.cli demo                                  # сквозной сценарий
python3 -m autosave.cli init-db savings.db                    # создать схему
python3 -m autosave.cli eod savings.db 2026-09-30             # EOD-начисление процентов
```

## Что было в кодовой базе

До этой задачи backend не было. В репозитории лежал только кликабельный прототип
`index.html`, где округление — это JS-функция `roundUp()` над моковыми данными: без счетов,
журнала проводок и процентов. Поэтому модуль написан с нуля. Прототип не менялся.

## План внедрения

1. **Модель данных** — `autosave/schema.sql`.
2. **Расчёт округления** — `autosave/roundup.py`, чистая функция.
3. **Платёжный конвейер** с Me-to-Me-проводкой и graceful degradation — `autosave/payments.py`.
4. **Outbox-воркеры**: повтор неудавшихся округлений и доставка push — `autosave/outbox.py`.
5. **EOD-начисление процентов** — `autosave/interest.py`.
6. **Объединённый push** — `autosave/notifications.py`.
7. **Тесты** — `tests/`.

## Модель данных

Все денежные поля хранятся в **тийинах** (INTEGER, 1 сум = 100 тийин), никогда не float.

| Таблица | Назначение |
|---|---|
| `card_accounts` | Карты клиента: баланс, валюта, статус |
| `deposit_accounts` | Накопительный депозит: `account_number`, `balance`, `currency` (UZS), `status` (ACTIVE/BLOCKED), `interest_rate_annual` (строка-decimal, напр. `'18.00'`), `accrued_interest_balance`, `last_interest_accrual_date`, `opened_on` |
| `auto_savings_settings` | `is_enabled`, `round_up_step` (1 000 / 5 000 / 10 000 сум), `target_deposit_account_id`, `safety_balance_threshold` (по умолчанию 50 000 сум) |
| `transactions` | `CARD_PAYMENT_ACQUIRING`, `SAVINGS_ROUND_UP_ME_TO_ME` (всегда с `parent_transaction_id`), `INTEREST_CAPITALIZATION`; `idempotency_key` уникален |
| `ledger_entries` | Двойная запись: у каждой транзакции сумма DEBIT = сумма CREDIT |
| `interest_accruals` | Одна строка на депозит и день (`UNIQUE`), поэтому EOD можно запускать повторно |
| `outbox_events` | Transactional outbox: push-уведомления и повторы округлений |
| `audit_log` | Пропуски и сбои округлений, отказы в оплате, начисление и капитализация процентов |

Гарантии на уровне БД: частичный уникальный индекс не даст одной покупке получить больше
одного успешного округления, даже если повторы выполнятся параллельно. Кроме того,
`CHECK`-ограничения запрещают отрицательные балансы и недопустимые шаги.

## Конвейер оплаты

`CardPaymentService.process_card_payment()` — всё в **одной ACID-транзакции**
(`BEGIN IMMEDIATE`; в PostgreSQL — `SELECT … FOR UPDATE` по строкам карты и депозита):

1. **Идемпотентность.** Повтор с тем же ключом возвращает исходный результат без второго
   списания. Тот же ключ для другой суммы или мерчанта → `IdempotencyConflict`.
2. **Покупка.** Проверки карты → списание → `CARD_PAYMENT_ACQUIRING`
   (DEBIT CARD / CREDIT MERCHANT_SETTLEMENT). Не хватает на покупку → `PaymentDeclined`,
   отказ записывается в аудит.
3. **Решение об округлении.** Пример: 23 400 при шаге 5 000 → `round_up = 1 600`.
   Округление пропускается с причиной в `audit_log`, если: фича выключена, нет депозита или он
   чужой, депозит заблокирован, валюта не совпадает, сумма кратна шагу, или
   `баланс_карты − покупка − округление < safety_balance_threshold`.
   Остаток ровно на пороге допустим.
4. **Me-to-Me внутри SAVEPOINT.** DEBIT CARD 1 600 → CREDIT DEPOSIT 1 600,
   `SAVINGS_ROUND_UP_ME_TO_ME` с `parent_transaction_id`. UPDATE-запросы повторно
   проверяют порог и статус депозита.
5. **Graceful degradation.** Если проводка упала (исключение, таймаут ядра депозитов),
   откатывается **только savepoint**. Покупка фиксируется, в журнал пишется `FAILED`-строка
   округления, а в outbox — событие `ROUND_UP_RETRY`. Магазин оплату получает всегда.
6. **Один push** ставится в outbox в той же транзакции:
   `Оплата 23 400 сум. В копилку (18% годовых): +1 600 сум 🎯 (Баланс копилки: 185 000 сум)`.
   Баланс карты в push не попадает: уведомления видны на экране блокировки.

**`RoundUpRetryWorker`** повторяет неудавшиеся округления с экспоненциальной задержкой
(по умолчанию 5 попыток). Перед проводкой он заново проверяет защитный порог по
*текущему* балансу карты. Если клиент уже потратил деньги, округление пропускается.
После успешного повтора клиент получает push только про копилку.

**`PushDispatcher`** доставляет push из outbox по принципу at-least-once.

## Начисление процентов (EOD)

`InterestAccrualService.run_eod(business_date)`:

- Проценты за день = `balance × interest_rate_annual / 100 / 365`, округление до тийина
  по банковскому правилу (half-even), расчёт в `Decimal`.
- Начисленное копится в `accrued_interest_balance`. В последний день месяца оно
  **капитализируется** в `balance` проводкой `INTEREST_CAPITALIZATION`
  (DEBIT BANK_INTEREST_EXPENSE / CREDIT DEPOSIT). Со следующего месяца проценты идут
  и на проценты.
- Повторный запуск за тот же день ничего не делает. Пропущенные дни догоняются по одному.
  Каждый депозит обрабатывается в своей транзакции, поэтому ошибка на одном не
  останавливает остальные.
- Каждое начисление и каждая капитализация пишутся в `audit_log`.
- Заблокированный депозит (BLOCKED) продолжает приносить проценты: блокировка касается
  операций, а не дохода.

## Что нужно решить до продакшена

- **Отмены и возвраты мерчанта.** Сторно округления не реализовано. В брифе прототипа
  это требование есть, в этой задаче — нет.
- **Шаги округления.** Здесь 1 000 / 5 000 / 10 000 сум (по задаче), а в прототипе
  `index.html` — 500 / 1 000 / 2 000. Их нужно согласовать.
- **Остаток для процентов.** При догоне пропущенных дней используется текущий баланс,
  а не остаток на конец каждого дня. Для точного расчёта нужны снимки EOD-балансов.
- **Бизнес-дата** передаётся явно. Планировщик должен считать её по Asia/Tashkent.
- **Инфраструктура.** Перенос на PostgreSQL: блокировки строк, `NUMERIC` для ставки,
  уровень изоляции `READ COMMITTED` + `FOR UPDATE`. Outbox — через Kafka или очередь,
  публикация через CDC или поллер.
